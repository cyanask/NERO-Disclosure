# 信息披露智能体工作流 v2

这是工作流设计稿，不是已部署的运行程序，也不是对某一具体事项的披露法律结论。按用户现有“七类板块入口”的产品配置设计，不在这里重新定义证券市场板块分类。

## 文件

- disclosure_agent_workflow_v2.drawio：三页原生可编辑流程图。第1页为主流程；第2页为知识库接入；第3页为 Verify、Gate 和回退规则。节点与连线均为独立图形，不是嵌入的一张图片。
- disclosure_agent_workflow_v2.mmd：同一业务逻辑的 Mermaid 文本源文件。调整箭头或节点文字即可修改图示；不等于已经更改业务执行器。
- workflow_notes.md：本说明。

在 draw.io / diagrams.net 中通过“文件 → 打开自 → 设备”打开 .drawio 文件。编辑后保留原生 .drawio 格式。三页在画布底部切换。

## 本轮的三个修正

### 1. 板块不是两个 Skill 的重复用户输入

入口固定脚本选择并锁定法规、案例、模板资源范围；后续 Skill 自动继承。不让 Agent 重新选择板块，不要求用户反复填写。底层仍要检查返回资料属于既定范围且版本适用。

先共用 Skill A（披露义务与时点）和 Skill B（文件与内容规划）。不同门槛、格式、材料要求放在被锁定的规则、模板和验证配置中；只有真正不同的必经分析顺序或程序需要附加逻辑分支，不机械复制十四套 Skill。

### 2. 客户历史披露库应独立于板块三库的职能

它提供该客户的既有公开事实、承诺、披露口径、事项进展、更正关系，不是规则来源，也不能因为过去漏披露就证明当前无需披露。

最小可用做法：保存已公开公告原文，建立来源、公告日期/编号、客户、事项标签、关联前序公告、更正/补充关系、数据覆盖截至时间等索引。优先覆盖正在持续的事项、仍有效承诺、近期定期报告及其更正，再扩充历史。

可使用同一存储系统按客户做逻辑隔离；没有必要每个客户复制一套物理数据库。权限与客户隔离应由工具或服务端强制过滤。公开公告可共享底层原文；未公开材料、审批和任务档案必须按客户与权限隔离。

历史库在 A 阶段帮助判断是否为已披露事项的后续进展，在 B 阶段帮助规划新增/变化内容，在模板适配及 Word 核验阶段帮助识别口径差异。未检索到不代表从未披露；公告金额也不是完整的内部交易台账。

人工认可 Word 后，文件先归档为“人工确认稿/未公开”。只有后续实际完成公开披露、核实正式来源和版本，才进入“历史披露公告库”。最终公开版本可能与制作阶段的确认稿不同。

### 3. 取消强制事实登记节点，保留内部最小事实状态

用户自然语言说明情况，由 Agent runtime + LLM 理解、拆解、判断需要调用的能力，不要求先填固定表单。Agent 在内部记录已知事实、来源、待确认问题和版本。只针对会改变结论或后续制作的缺口追问。

“事实由模型整理”不代表“未知事实由模型补齐”。重要理解可以随判断结论一并展示给用户确认，不另设一轮固定事实审批。

## 节点与绑定

| 节点 | 执行能力 | 前置审批 | 主要输出 |
|---|---|---|---|
| 入口 | 固定脚本 | 无 | 只读板块/客户资源范围 |
| A | Agent runtime + LLM + Skill A | 入口范围有效 | 义务、时点、理由或事实缺口 |
| B | Agent + LLM + Skill B | 有效的 A 人工确认 | 文件清单、内容颗粒度、依据、材料缺口 |
| T | 模板检索与匹配工具 + Agent 适配 | 有效的 B 人工确认 | 模板与规划的对应方案 |
| W | Agent 组织正文 + Word 生产工具 | 有效的 T 人工确认 | 可审阅 Word 文件 |
| 交付 | 归档工具 | Verify W 通过且人工确认当前文件 | 人工确认稿、证据与审批记录 |

不强制每个节点新增一个 Skill，也不要求每个节点独立 Agent。两个核心 Skill 在专业判断环节提供方法；模板和文件生产可复用已有工具。

## Verify 与 Gate

Verify 输出检查报告；自动 Gate 读取报告决定补充、修复、提交人工或升级；用户的四次确认就是四个人工 Gate。

自动检查不等于合规保证。字段、版本、权限、引用定位与算术适合脚本；适用性、重大影响、案例可比性和内容完整性的语义判断可由 LLM 辅助复核，重要争议交人工。争议或警告不得被隐藏；人工应看见它们以及相应依据。

自动 Gate 的“通过”是满足本节点提交审阅的条件，不代表所有后续文件材料都已经齐备。B 可以明确列出待补材料；进入可交付 Word 时仍有必填关键事实缺口，不得用模型虚构值填齐。

## 状态机和审批有效性

主状态建议为：scope_locked → assessing → awaiting_obligation_approval → planning → awaiting_plan_approval → selecting_template → awaiting_template_approval → producing → awaiting_document_approval → approved_draft_archived。

补充状态：awaiting_information、revising、manual_escalation、no_disclosure_monitoring。

审批应绑定本次事实、判断、规划、模板和文件的具体版本。后续节点只接受有效的上游版本。事实或依据发生实质变更时，定位最早受影响节点，使受影响下游审批失效，再重新检查和确认；不必对仅版式修改从头重跑。

回退顺序：事实/义务问题 → A；文件或内容要求 → B；模板结构 → T；措辞/排版 → W。后续阶段发现关键事实缺失，应重新评估它是否改变义务判断，不能所有问题都留在排版节点修复。

重试必须有上限。持续缺资料、反复失败、存在紧急披露时点或规则解释争议时，进入人工升级；等待和重试不暂停时限提示。具体时限与计算口径从已锁定适用规则中读取，不在共用 Skill 中硬编码。

这些约束需要由现有执行器、工具入口和状态存储实施。只改图或只把顺序写进 MD，不会自动让 Agent 无法越过审批。

## 与实际对外披露的边界

本图以“文件制作完成并获人工确认”为终点，不包含报送、正式发布及其他公司法定程序。产品中的人工确认不当然替代公司应履行的董事会、审计委员会或其他法定/内部程序。
