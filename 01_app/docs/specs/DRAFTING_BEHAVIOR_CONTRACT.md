# 起草与 Word 制作行为合同

版本：1.0.2。状态：已接入起草核对、明确留空制作及失败续接；自动化验证与真实模型、人工验收分别记录。

## 责任与真源

同一个 Pi 主控负责理解需求、判断规则适用、核对资料和解释自然语言选择。运行系统负责工具权限、文稿范围、版本保护及用户选择的登记。Word 工具负责按已准许的内容生成文件，不负责决定是否应当绕过缺口提醒。

使用现有会话 runs.body 中的 document_preflight 和 journal 留存核对记录、缺口提醒与用户原话，不增加数据库表、第二个控制器或新的发布流程。旧事项中的 requirements、drafting_gaps 和 documents 作为已有内容基准提供给主控；不机械继承旧流程单文件限制或全部审批节点。

## 行为顺序

1. 分流只确定本轮目标。首次说“拟个公告”进入文本准备；明确要求 Word 或修改已有 Word 时进入文件准备。两者最初都只提供读取、检索和起草前核对工具。
2. 主控结合当前资料、规则、模板和既有要求，登记文稿范围、核对主题及结构化缺口。
3. 存在未告知的内容缺口，通常登记提醒并以 waiting_user 结束本轮。若本轮用户已经明确要求缺项留空或标注待补并先制作，主控以 draft_with_placeholders 登记完整原话和具体缺口后继续，不再要求重复选择。单纯要求 Word、提问、否定或假设性表达不构成这一选择；存在事实冲突时仍先核对，不据一般留空指令选择某一种事实。
4. 用户之后明确接受同一文稿的已告知缺口，主控引用提醒编号及完整本轮用户消息登记选择。系统核对会话、公司、文稿范围及消息先后关系，之后开放正文保存或 Word 工具。
5. 没有内容缺口时可直接开放后续工具。已接受的相同缺口可沿用；每轮仍重新核对新资料和本轮目标。新增缺口、冲突加重或文稿范围改变时重新提醒。
6. 保存前再次检查文稿范围、核对输入指纹和正文占位。新发现的内容缺口回到提醒，不按执行失败处理。来源定位异常退回主控自行修正，不直接改写成用户事实缺失。

接受缺口仅授权制作工作稿，不是正文正确性确认、文件定稿、法定审批或发布。前轮提醒后的“确认”不能被送入正文确认接口；含否定、疑问、换事项或仅补部分资料的回复不得作为同意。自然语言语义由主控判断，运行系统不以单一固定口令代替理解。

## 缺口登记与正文

每份文稿登记 title、kind、已有 document_id、checked_topics 和 gaps。每个 gap 保存 label、reason、category、state；同类别相同 label 合并，冲突状态优先。label 不带“待补”前缀，后续评估及正文占位沿用它。

| 类别 | 处理 |
| --- | --- |
| content | 正文事实缺失或冲突；先告知，经接受后在正文对应位置使用具体占位 |
| evidence | 系统检索、引文或来源定位问题；回到主控修正，保留诊断，不伪装成用户遗漏 |
| review | 后续内容或版式复核；保留登记，不强行作为正文缺失 |
| publication | 签发、盖章、报送或发布待办；保留登记，不要求先完成才起草 |

禁止把占位正文、待补清单和检查日志彼此反复复制。正文未覆盖已经接受的内容缺口时，由主控在相应位置补占位，不由渲染器把整张清单追加到文末。既有人工 Word 继续使用锚定修订和旧版本保护。

## 权限与恢复

assess_document_readiness 是生产工具开放的前置调用。仅 ready 或 authorized 且输入指纹仍匹配的核对记录允许保存。缺少有效记录时回到核对工具；文稿范围不匹配时撤销本轮开放状态。跨会话来源、损坏文件、旧版本修改等原有保护继续生效。

提醒和选择持久化在原会话记录中。文稿第一次保存后，核对记录的标题身份关联到该文稿编号，已接受缺口随同一文稿继续有效；其余环节按编号或标题解析为同一文稿。上下文切换同时更新运行记录的 system_sha256 并登记 context_loaded，使 Pi 启动回执校验与后续节点一致。重启不伪造用户选择，也不自动重放生产操作。新轮次重新检查当前事实与文稿；相同文稿、相同已接受缺口的选择可以复用，相关追问或补充通过 drafting_notice_id 保留提醒关联，但不产生新同意；无关中间任务不携带隐含同意。已真实登记的核对记录可从紧邻的 failed、incomplete、interrupted 轮次恢复，取消轮次不自动携带该记录；未调用核对工具的模型文字不能当作已登记选择。请求去重、取消、原稿保护和文件登记继续由既有 runtime/document_store 负责。

内部纠偏按当前阶段实际开放的工具执行，不要求调用其他阶段工具。内部纠偏和收尾消息标记 runtime_control，后续恢复时不作为用户追加要求；旧记录仅在真实用户日志没有对应原话时识别内部提示。原始日志与检查点保留，恢复视图区分未完成模型文字与真实回执，并保留工具调用及返回的配对。界面遇到自动重试时只突出本轮最后一条答复，其余答复可在工作过程查看。model_call_started 与 model_tool_surface 分别记录调用时工具名和协议转换后的工具名，不记录凭据或请求全文。

## 行为用例

- 只说“更换董秘，拟个公告”，资料不足时先收到提醒，不出现正文或 Word 文件。
- 首次仅要求 Word、内容不足时先提醒；回复接受后能够生成待补草稿。首次已明确要求缺项留空或标注待补时，完成核对登记后直接继续。
- 仅补部分资料或反问时，不被当作同意；已接受的同一缺口不反复询问。
- 更换文稿、新增缺口或冲突加重后，原选择不能直接放行。
- 正文占位不重复嵌套、不在文末堆叠，系统依据问题不混入用户资料缺口。
- 文件仍出现在会话及交付文件清单中，保留版本和待补状态，不变成已定稿。

自动化回归包括模拟模型的失误分支，而不只测试预设正确工具调用。test_stability_e2e.py 使用真实 Python 后端、Pi 子进程、本机 HTTP 模拟服务及 Word 子进程，分别覆盖 Completions 和 Responses 协议；验证误答后纠偏、选择续接、下载、待审阅状态及请求去重。test_stability_recovery.py 覆盖已登记选择在失败后的恢复以及取消、换文稿时的隔离。外部模型判断质量、正式 App 页面效果与用户人工接受不由这些测试代替。
